# D3.2 — table/evidence/comparison and correctness export

Implementation version `d3.2.v1`, policy `d32-table-evidence-v1-proposed`.
Proposed, not frozen. D3.1 scalar/OCR behavior and CLI remain available.
No production normalization, shared schema, gold, training or inference is changed.

## Matching and metrics

Only explicit gold `present` cells generate matching features. Description uses
NFC, case-sensitive whitespace collapse and token-set Jaccard, quantized down to
integer thousandths; other cells use exact canonical equality. Description score
has weight 4, each other equality weight 1. An edge needs description Jaccard
>=0.5 OR at least two other exact present cells. Otherwise its weight is zero.
Numeric quantity/unit_price/line_total use D3.1's canonical nonnegative decimal
string rules and Decimal equality. Invalid predictions never equal invalid gold.

Hungarian maximum-weight assignment has dummy vertices for unmatched rows.
Gold/pred indices ascend and only strict improvements update the solution. This
is the deterministic algorithmic tie-break; index proximity is not a feature.
Forbid each selected edge and solve again: unchanged optimum marks its identity
ambiguous, including global ties. Deterministic scores retain such pairs, but
calibration/evidence exclude ambiguous row identity. Report every pair's features,
score, ambiguity, the entire feature matrix, and unmatched indices.

Whitespace wrapping within one description normalizes naturally. Physical rows
split by a producer are not merged; fragments and duplicated rows remain visible.
Token sets intentionally ignore token order/multiplicity **for matching only**;
cell correctness still compares the full normalized string. Common quantity/unit
values can create weak or ambiguous matches; this proposed threshold needs consumer
review, not tuning on holdout. All tables support the business maximum 30 rows;
unknown columns/non-object rows/oversized arrays are invalid, retained in errors,
and scored as missing table predictions. Missing/failed/duplicate sample records
have no selected payload, as in D3.1. Gold without `items` is an unlabeled table.

| Metric | Numerator | Denominator |
| --- | --- | --- |
| Matched cell accuracy | Correct labeled cells in matched rows | Present + absent cells in matched rows |
| E2E cell accuracy | Same correct cells | Present + absent cells in all gold rows, including missing rows |
| Exact row accuracy | Matched fully labeled rows with all five cells correct | All gold rows whose five cells are present/absent, including missing rows |
| Column accuracy | Correct labeled column cells in matched rows | Labeled column cells in matched rows |

Missing labels are unlabeled. Obscured/unlabeled cells are excluded, not null
truth; partial rows cannot count as fully exact. A missing row contributes zero
correct cells even for absent slots. Zero denominator is null, including empty
tables. Raw gold/predicted/matched/missing/extra rows and empty/unlabeled/invalid
counts accompany metrics. Duplicate signatures use all five canonical cells;
counts are repetitions beyond the first in each side. Excess duplicates count
repetitions above `max(1, gold multiplicity)`; a unique hallucinated row is extra,
not a duplicate. Exact-row accuracy does not penalize extras in its numerator;
inspect extra/duplicate counts alongside it.

## Evidence adapter and scoring

D3.2 loads and hash-checks gold, labels, transcript, regions and canonical PNG.
It checks PNG signature/IHDR dimensions against annotation dimensions, without
image libraries or model loading. The only supported gold convention currently is
`renderer-local-v1; not approved shared geometry`, top-left, page0, pixel units:

- D1.2 identity render: bbox pixels -> normalized quad TL/TR/BR/BL.
- D2.2 affine renderer: `quad_px` is already canonical, normalized by its output
  dimensions; source/canonical affine vectors must be finite six-element arrays.
  No transform is applied a second time. Missing/unsupported geometry is excluded
  with reason, never a guessed bounding box. The affine metadata is descriptive;
  this evaluator does not certify invertibility of producer preprocessing.

Gold pointers must be annotated `present`; null pointers/headings and other label
statuses do not become evidence truth. Multiple annotated regions at a pointer
are all expected, in stored annotation text order, including repeated printed
occurrences. This strict all-occurrences policy requires AI-1 review.

Offline prediction records optionally carry `canonical_page` (page/width/height/
sha256), `geometry_convention: "canonical-normalized-quad-v1"`, and
`field_metadata` in the shared O4.1 shape (`path`, `source_regions`, `review_flags`).
The convention explicitly declares normalized top-left convex clockwise quads;
strict convexity/finite/range/page0 are checked. Canonical hash, page and dimensions
must equal the gold page. Producers own export from compute response; no automatic
interpretation of processed coordinates. Item pointers follow the table assignment.
Duplicate metadata paths and flags containing `ambig` exclude that association.

Convex polygon clipping computes IoU, never axis-aligned envelopes. Region pairs
with IoU >=0.5 are matched one-to-one by maximum sum of IoUs, rounded to millionths.
Region alternative optima are reported. Coverage is available unambiguous fields /
annotated fields. Geometry recall is matched regions / all supported annotated
regions, including unavailable predictions as zero; accuracy-on-available uses
annotated regions at covered fields only, and precision uses predicted regions at
those fields. Missing/incompatible/invalid evidence has zero E2E success and no
positive available-only score. No supported gold => null scores and reason counts.

Text association uses an **optional offline extension** `evidence_text` on field
metadata: exact NFC/whitespace match to joined annotated region texts. It is not
`raw_value`, payload text, or OCR score, and is not a shared schema change.
Without explicit text association output, text accuracy-on-available is null.
Canonical compatibility is required for text comparison too. Report text support,
coverage, E2E accuracy, raw texts, geometry matches and ambiguity separately.

## Comparison and calibration protocol proposal

Run all available frozen candidates through the same evaluator. Full B0/M0/M1
comparison is fair only if all three exist with identical nonempty string pins:
`dataset_manifest_sha256`, `dataset_version`, `preprocess_version`,
`normalizer_version`, `ocr_version`, `schema_version`. Missing pins are a mismatch,
even if missing on both sides. Manifest hash must match the exact file; a declared
dataset_version must match manifest dataset_version (fallback version). Reports
include per-type/family/quality/has-absent/table-row-count slices, scalar/OCR/table/
evidence metrics and failed-job accounting. Missing family/quality is `unknown`.
No adapter guesses producer versions or invents a missing candidate.

No implemented calibration protocol exists in this checkout. The explicit proposal
`d32-correctness-v1-proposed` exports per scalar/gold row cell and unmatched extra
candidate: sample/field/prediction pointer, candidate name/version/value, gold,
status, 0/1/null correctness, outcome, eligibility and exclusion reasons, split,
partition, evaluator/policy/normalization/protocol versions and artifact hashes.
Extra rows have no field gold: unlabeled, correctness null, ineligible.

Eligibility requires manifest `split=dev` and `dev_partition=dev-calibration`, all
comparison version pins, producer `calibration_protocol_version` equal to this
proposal, labeled unambiguous identity, successful prediction and a nonempty
candidate. A wrong or invalid nonempty candidate may have correctness=0 and be
eligible; absent false fills are negatives. Missing/null candidates, obscured,
unlabeled, failed jobs and ambiguous identities retain trace records but are not
fit inputs. Final/train/tuning/unpartitioned samples are always ineligible.
This is data eligibility under a proposal, not Lead approval or evidence of enough
class/family support. AI-2 owns calibrator fitting. No fitting occurs here.

Freeze record is `prepared_not_frozen`, decision null, with evaluator source hash,
consumed asset hashes, policies and required reviewers. Policy/metric changes
require a version bump and rescoring every candidate under the same definitions.
Only a corresponding reviewed decision can authorize an actual freeze.
